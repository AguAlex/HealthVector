### Stakeholder Interview Simulation (Patient)
**Product Owner**: Hello! We are building a medication assistant. How do you currently manage your treatment, and what difficulties do you face?
Patient: Hi! I take several pills a day, and it's hard to remember everything. I would like an app where I can simply type the names of the drugs to add them to a list, or delete them if the doctor takes them off my prescription.
Product Owner: Understood. How would the app help you not forget them?
Patient: I'd like it to automatically generate a daily schedule for me. When it's time to take a pill, I want an alert to appear on the screen. After I take it, I want to press a button to mark it as "taken", or if I forgot, to mark it as "missed".
Product Owner: Do you read the medication leaflets? Do they help?
Patient: The writing is too small. I would like to ask questions directly in the app, like "can I take this with milk?", and get an answer. I also want to quickly see what side effects a pill has.
Product Owner: Do you have any other preferences regarding how the app looks or works?
Patient: Yes, sometimes I make mistakes and want to delete everything (a kind of reset). I'd also like to be able to copy the schedule as text to send it to my daughter. Regarding the appearance, I have vision problems, so the text must have high contrast and be clear. I will use it on my laptop, but also on my phone.
## Elicitation Record
Interview notes (INT)
*   INT-1: The patient wants to easily add and remove medications by name using an active list.
*   INT-2: Automatic daily schedule generation is required, and the user wants to view the side effects of each medication.
*   INT-3: The patient needs a visual alert at the scheduled dose time and an option to mark the dose as "taken".
*   INT-4: The user wants to mark a dose as "missed" if they forgot to take it.
*   INT-5: The patient wants a chat feature to ask natural language questions about medications.
*   INT-6: A general "Reset" button is required to completely clear the schedule and current data.
*   INT-7: The patient wants to export the schedule as plain text to share with relatives.
*   INT-8: The interface must be accessible for elderly people (high contrast, clear text).
*   INT-9: The application must be readable and usable on both a laptop monitor and a phone screen (responsive design).
## Documents used (DOC)
*   DOC-1: Requirements and constraints from the lab document: not medical advice, API keys must be read from environment variables, and the system must handle rate limits gracefully (HTTP 429).
*   DOC-2: Public leaflet model (e.g., Paracetamol), demonstrating the need to cite the exact section to ensure answer traceability.
## Team decisions (DEC)
*   DEC-1: All answers will be extracted strictly via RAG from the indexed official leaflets to prevent hallucinated medical advice.
*   DEC-2: Any entered drug not found in the leaflet database will be blocked with a clear error message to avoid generating unsafe schedules.
*   DEC-3: The maximum response time for interaction checks will be set to 5 seconds.
*   DEC-4: Personal data will not be sent to the LLM API; only drug names and queries will be processed to ensure privacy.
*   DEC-5: The application will run locally on standard developer hardware configurations (minimum 8GB RAM).
*   DEC-6: The initialization of the vector database for leaflets at system startup must take under 10 seconds.

## Road map
This is the macro execution structure, designed for a 4-6 week period.
Labs 1-2: Planning and Architecture
*   Definition of functional and non-functional requirements.
*   Initialization of the Kanban board and Gantt plan.
*   Collection of leaflets and setup of the basic technical environment (MCP servers).
Labs 3-4: Development and MVP Version (MVP Ready)
*   The RAG pipeline is functional and can answer questions based on the leaflets.
*   The basic daily schedule is generated.
*   Milestone: Launch of the basic version (MVP), usable internally.
Lab 5: Cross-Testing (Adverse Review)
*   The Version P team tests and evaluates the application of a Version D team (and vice versa).
*   Identification of defects, edge cases, and "hallucination" errors.
*   Milestone: Evaluation report (Adverse review) completed.
Labs 6-7:
*   Fixes and LaunchIntegration of feedback from cross-testing.
*   Refinement of the UI and error messages.
*   Milestone: Presentation of the final prototype (Launch).

1\. Setup repo and environment variables (.env) \[NFR-04\]
*   Given: A developer clones the repository and inspects the codebase.
*   When: The system is prepared for execution.
*   Then: No hardcoded API keys exist in the code, and all keys are securely loaded from a `.env` file.
2\. Create "Not medical advice" banner in UI \[FR-12\]
*   Given: A user opens the application on any device.
*   When: The main dashboard or chat interface loads.
*   Then: A persistent, highly visible banner explicitly states that the app provides no professional medical advice.
3\. Implement UI for adding medications \[FR-01\]
*   Given: A user is on the main dashboard viewing their active list.
*   When: The user types a drug name (e.g., "Aspirin") and clicks "Add".
*   Then: The medication immediately appears in the active medication list on the screen.
4\. Implement medication deletion function \[FR-02\]
*   Given: The user has "Aspirin" in their active medication list.
*   When: The user clicks the "Remove" button next to the drug name.
*   Then: "Aspirin" is completely removed from the active list and the schedule.
5\. Collect and index leaflets (Vector DB) \[Data\]
*   Given: A folder containing 5-10 PDF/TXT public drug leaflets.
*   When: The database initialization script is executed.
*   Then: The leaflets are chunked, vectorized, and stored in the vector database in under 10 seconds.
6\. Create RAG pipeline for leaflet search \[FR-09\]
*   Given: A user submits a query about a medication.
*   When: The RAG pipeline processes the question.
*   Then: The system returns an answer based strictly on the indexed leaflets, without generating hallucinated medical facts.
7\. Handle "Medication not found in DB" error \[FR-11\]
*   Given: The user attempts to add an unknown drug (e.g., "FakeDrug").
*   When: The system checks the vector database for the corresponding leaflet.
*   Then: The system blocks the addition and displays a "Not found in database" error message.
8\. Configure MCP server for interactions \[Arch.\]
*   Given: The orchestrator agent needs to evaluate a medication list.
*   When: The agent triggers the interaction checking MCP tool.
*   Then: The MCP server successfully returns structured interaction data to the agent for processing.
9\. Implement medication interaction warning \[FR-07\]
*   Given: The medications Paracetamol and Warfarin are added to the active list.
*   When: The system generates the schedule or analyzes the list.
*   Then: A clear visual alert is displayed warning the user about a potential drug interaction.
10\. Generate daily medication schedule \[FR-03\]
*   Given: The user has multiple verified medications in their active list.
*   When: The user requests to view their daily plan.
*   Then: A timeline is displayed showing specific dose times (e.g., 08:00 AM) for each drug.
11\. Add button and logic for "Dose taken" \[FR-05\]
*   Given: A scheduled dose time has arrived on the daily timeline.
*   When: The user clicks the "Take" button next to that specific dose.
*   Then: The dose status updates to "completed" visually and in the system log.
12\. Chat function (Q&A) based on RAG \[FR-08\]
*   Given: A user is interacting with the chat interface.
*   When: The user asks a natural language question (e.g., "Can I take this with food?").
*   Then: The system provides a clear answer based on the RAG pipeline output.
13\. Extract and display source (leaflet section) \[FR-10\]
*   Given: The chat system generates a response to a user's medical question.
*   When: The response is rendered on the screen.
*   Then: The response includes a visible citation pointing to the exact leaflet and section (e.g., "Source: Paracetamol Leaflet §4").
14\. Filter/anonymize data sent to LLM API \[NFR-03\]
*   Given: The user generates a schedule or asks a question.
*   When: The system constructs the prompt for the external LLM provider.
*   Then: Network logs confirm that no personal identifiable information (PII) is included in the payload.
15\. Handle HTTP 429 errors (LLM Rate Limit) \[NFR-02\]
*   Given: The external LLM API exceeds its free-tier rate limit and returns an HTTP 429 error.
*   When: The system attempts to fetch a response from the API.
*   Then: The application catches the error, does not crash, and displays a graceful "API limit reached" message to the user.
